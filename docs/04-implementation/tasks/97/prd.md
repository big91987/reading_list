# Issue #97 PRD：页面版本号显示

日期：2026-10-03。状态：Ready for Architecture（Runner 自主推进策略下的需求就绪，非用户逐项批准）。

## 1. 背景与证据

用户要求“页面上增加版本号显示，当前希望是0.1.0 rc2”。目标是在读书清单页面直接辨认产品版本，便于描述自己使用的版本。当前工作区 `app/index.html` 有标题、添加区、清单区和页脚“一本一本，慢慢读完。”，没有版本标识；`app/` 中未发现既有产品版本声明。`deploy/release.json` 记录兼容性和内容摘要，不是用户可读版本号。本任务以用户给出的版本文本为权威，不推断其已发布状态或实际部署时间。

项目现状文档供背景参考；具体行为以本轮代码为准。未采集用户使用频率或量化支持收益，不虚构统计。页面目前不能直接查版本，使用者只能通过页面外材料或询问维护者核对（可行替代方式，未采集实际使用证据）；本轮补充直接可见的标识，不建设版本管理平台。

## 2. 目标、成功标准与非目标

- G-01：用户打开现有读书清单页面即可找到并读出当前版本 `0.1.0 rc2`，不需要打开设置、悬停或点击。
- G-02：显示版本不改变书单操作、数据和阅读体验。
- 当前阶段交付完整“打开页面 → 查看版本 → 继续使用书单”闭环；全部需求为本次必需。
- 非目标：版本历史、更新通知、关于弹窗、版本编辑入口、自动取 Git/远端发布信息、自动升级、缓存更新治理、多页面扩展、账号或服务端改造。
- 后续边界：维护者要求自动发布同步或多版本追溯时另立需求；本轮不预建相关能力。

## 3. 用户、运营模式与责任

直接用户为现有读书清单使用者，通过原有页面访问方式获得展示，查看后继续添加、修改、筛选及阅读，无需注册、授权或额外配置；关闭页面即退出本次查看，不产生用户侧版本记录。

维护者负责声明产品版本、通过既有受审查产品变更更新它，并在既有发布流程下交付及核验页面。设计阶段负责可读性和布局，开发负责实现及自动检查，独立 QA 复核 AC。现有项目 Owner 承担支持、范围和发布风险责任；本轮不新增运行服务、预算、容量角色或外部财务承诺。发布与最终 PR 合并仍遵循项目人工授权边界。

## 4. 产品级业务架构与对象

产品新增只读版本识别能力，业务结果为用户准确描述页面标识。价值流：维护者声明版本 → 经既有变更/发布流程首次提供 → 用户打开页面并查看 → 继续使用书单 → 维护者在未来版本变更时更新并核验。具体版本维护载体由设计定义，不提供终端用户编辑入口。

核心对象为“页面版本标识”：本次来源是 Issue #97 的 `0.1.0 rc2`；首次可用条件是交付页面按 AC-01 正确呈现；变更由维护者通过产品变更完成；旧版本随后续页面版本替换退出展示。业务不变量为展示值与该产品交付声明一致，不从用户书籍数据推算，不用部署摘要替代。书籍清单及其生命周期沿用现状。

正常流程无需交互或持久化。空清单、筛选无结果及现有操作错误状态下，版本标识仍可查看。若标识缺失或文本错误，由维护者修复页面交付，不要求用户清理 localStorage 或改书单。版本展示无新增外部依赖；底层部署与 Harness 只沿用既有责任，不属于新增产品能力。

## 6. User Story

- US-01：作为书单使用者，在页面已打开时，我希望直接查看当前版本，以便准确描述所使用的产品；清单为空或筛选无结果不影响查看，没有点击动作或数据副作用。
- US-02：作为已有书单的使用者，我希望版本标识不影响阅读和操作，以便继续使用原有清单；窄屏、键盘和触屏可继续操作，已有数据及错误恢复行为保持原样。

## 8. 依赖、风险、假设和设计输入

依赖现有静态页面及项目浏览器能力，无新增外部服务。非阻断假设：用户所说版本指本次交付的产品标识，不是实时查询已部署实例；页脚是低干扰展示位置，允许滚动；未来版本由维护者经现有产品变更维护。依据和影响见决策台账。
