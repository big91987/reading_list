# Issue #71 HLD：原条目修改书名

> v1 · Accepted · 2026-10-02
> 产品规则来自已批准 [PRD](../../../04-implementation/tasks/71/prd.md)，不重开需求审批。
> A-001～A-003 已由用户明确接受推荐方案，见 [决策台账](architecture-decisions.md)；以下目标视图承接需求，具体实现建议见第 7 节。

## 1. 目标、运营与边界

用户在同一本书上修正名称，不丢失阅读状态、位置和当前筛选。产品 Owner 审查设计；研发负责实现、LLD 和完整 AC 证据；Runner 负责最终检查及任务分支／草稿 PR 发布。不新增账号、服务端、跨设备同步、标签或评分。

系统是现有静态 HTML/CSS/JavaScript 浏览器应用。用户通过现有新增入口创建持久书籍；加载有效本地数据后即可编辑、标记和删除。书籍属于清单管理责任；筛选、统计是派生视图，编辑草稿仅在当前页面内存存在。浏览器清理数据、多标签页冲突解决不在承诺内。

```text
已批准 PRD / AC
  → 本阶段：交互原型 + HLD + 数据/本地操作契约 + G2 自查
  → Owner 确认设计
  → 研发：LLD / 实施计划 → app 实现 → 全 AC / 既有主线验证
  → Runner 检查与发布草稿 PR（不自动合并）
```

## 3. 系统上下文、逻辑与事实源

```text
个人用户（桌面/手机）
    │ 输入、按钮、键盘/输入法
    ▼
交互呈现 ──明确保存命令──▶ 清单管理 ──候选快照──▶ 本地保存
    ▲                       │                    │
    └──错误/成功/派生视图────┘              浏览器 localStorage
         草稿只在内存                        同源持久 JSON
```

| 责任 | 输入／输出 | 拥有的状态 | 不负责 |
|---|---|---|---|
| 交互呈现 | 开始编辑、取消、保存、筛选、焦点和反馈 | 当前筛选；唯一草稿和条目关联；条目错误 | 不直接改持久书名，不把草稿混入新增／标记／删除 |
| 清单管理 | 校验、构造改名候选、协调其他清单命令；输出派生可见书籍和统计 | 最后成功保存的内存清单；顺序／read 不变量 | 不把视图下标或名称当持久身份，不持久保存筛选／草稿 |
| 本地保存 | 读旧格式；串行写完整候选 JSON；输出成功／失败 | `page-between-reading-list` 保存结果 | 不承担云同步、备份或多页冲突调和 |

持久书名的权威来源是最后成功写入的本地清单；页面中的清单仅是该结果的内存镜像。当前筛选、错误和草稿属于临时 UI 状态。总数、已读数、可见列表只从已提交清单派生，没有第二份权威统计。

## 4. 关键同步流与状态

1. 用户通过新增创建或从旧存储加载目标书籍；进入编辑时预填保存名、聚焦输入，条目仍可标记／删除。
2. 输入只更新唯一草稿。保存命令按空名、原始输入长度、整个清单重名校验；排除目标自身。
3. 校验通过后构造只变更目标 `title` 的候选，不修改当前内存清单。同步尝试写入完整 JSON。
4. 写入成功后才替换内存清单、清除草稿、派生视图并播报成功；焦点回目标编辑按钮。失败保留原清单与草稿，显示条目错误并聚焦输入。
5. 取消、切换筛选、编辑另一书、刷新仅丢弃草稿。标记／删除／新增遵循契约协调矩阵，不把草稿写入候选。

```text
展示 → 编辑 → 校验失败 ──修正──┐
        │       ▲            │
        ├─保存──校验───────────┘
        │        └─有效→写入失败→编辑（保留原名/草稿）
        │               └─成功→展示（新名）
        └─取消/筛选/换条/刷新/目标删除→展示或条目消失
```

所有命令在页面事件内同步串行执行，无后台任务、调和循环或 API 网络调用。重复保存原名允许退出；刷新重载最后写入结果。该局部重试不是跨标签页的幂等／并发承诺。

## 5. 部署、信任与故障

部署单元沿用 `app/` 三个静态文件，在用户浏览器运行；现有静态托管方式不变。原型是独立静态目录，使用隔离存储键和演示数据，不替换产品、不迁移真实清单。

书名和历史 JSON 都是不可信用户数据：按原加载兼容策略读取，用 `textContent`／输入值呈现，不将名称插入 HTML。应用只能访问当前浏览器当前源可用的存储；不引入凭证、上传或远端遥测。

| 故障 | 边界与责任 | 可观察结果／恢复 |
|---|---|---|
| 空、重名、超限 | 清单管理校验 | 不写入；输入保留，可修正／取消 |
| 写入抛错 | 本地保存 | 不提交内存候选，不显示成功；保留草稿；恢复存储后重试 |
| 刷新／页面关闭 | 浏览器生命周期 | 丢弃草稿，从保存清单加载；筛选回到既有默认全部 |
| 旧数据结构、坏 JSON／读错误 | 本地保存沿用加载策略 | 不因加载触发覆写、批量去重或截断；加载失败无额外恢复／备份承诺 |
| 标记后目标离开筛选／目标删除 | 清单管理协调 | 结束该条编辑，焦点回当前筛选或相邻有效操作 |
| 同源其他标签页写入／用户清理存储 | 既有环境边界 | 不新增冲突处理／备份，本轮明确非目标 |

## 7. 方案比较与技术选择（已确认）

目标责任已由需求约束；建议继续原生 DOM、原位表单、内存草稿、本地快照提交，不引入新框架。

| 方向 | 匹配与代价 | 状态 |
|---|---|---|
| A：原生 DOM + 候选快照先存后提交 | 沿用当前产品，改动集中；需处理每次重绘的草稿与焦点，失败分支可测试 | 已接受，A-001～003 Accepted |
| B：先改内存再回滚 | 代码局部短，但失败时需恢复对象、派生状态与编辑关联，增加中间不一致风险 | 未选 |
| C：新增状态框架／持久 ID 与迁移 | 对本轮没有额外业务结果，引入依赖和历史数据迁移、主线回归成本 | 未选 |

建议的窄接缝是校验、候选写入、交互状态三个函数责任，不要求三份文件、抽象适配器或微服务。所有保存结果使用同一成功门槛，新增／标记／删除协调只覆盖编辑相关路径及必要失败处理，不扩展独立功能。

无难以逆转的新选择：不变更存储 schema、键或外部 API，故无需独立重大 ADR；本文件比较与决策台账保留完整记录，没有裁剪原型、HLD、契约或追溯。

## 8. 演进、退出与 LLD 输入

研发需要补充 DOM 更新／焦点映射、内部函数接口与测试注入点的 LLD。清单身份使用当前加载周期中目标对象关联，不增加持久 ID；全数组构造候选时必须维护或重新绑定正在编辑的对象关联，不使用筛选后的索引或 title 查找写入目标。

不做 schema migration；移除编辑 UI 仍可由旧应用读取改名后的 `{title, read}` 数组。兼容测试失败则阻止交付，不静默改存储。未来跨设备、历史撤销或多页冲突只有进入新需求后再设计，当前不预建扩展体系。

已知验证缺口：真实操作系统中文输入法、屏幕阅读器、旧数据 fixture 深比较、真实存储异常及产品完整验收属于研发责任，详见 [证据](../../../05-validation/tasks/71/design-validation.md)。G2 自查见 [审查报告](../../../04-implementation/tasks/71/design/g2-review.md)，用户已明确批准设计并授权进入研发；Escape 原型补测通过，补充证据不改变设计，不需重复审批。
